# Source specification — Bank Account Event Notifications

## Project

Greenfield Java 21 / Maven 3 current-account project. The Banking operations ticket is the user-facing story: withdrawals and incoming deposits, each with a payment, transfer, or Pix transaction-kind input, update the balance and can produce account events. No separate payment/transfer/Pix account methods. Use a single Maven module: `pom.xml`, `.gitignore`, `src/main/java/bank/notifications/` (account, transaction kind, immutable event/context, observer contract, recipient-aware notification reaction, separate in-process SMS and WhatsApp senders), and `src/test/java/bank/notifications/` (executable contract tests). Choose exact domain class and callback signatures in the source work; the grounded design shape is a subject registering multiple interface-typed observers and invoking their common callback with event context, not an external event bus. Composition/registration outside the account decides which observers receive which events. The account must never import or construct a concrete sender. Use `BigDecimal` for BRL balances and exact comparisons; no external gateway or JSON dependency.

The source should read as the requested banking service, not a generic sensor demo. Four independent event conditions: (1) withdrawal moves balance from >= 0 to < 0: manager, (2) withdrawal amount >= R$5,000 and < R$10,000: manager, (3) withdrawal amount >= R$10,000: digital security, (4) incoming transaction moves balance from < R$50,000 to >= R$50,000: investment management. A single large withdrawal may generate both an overdraft and large-withdrawal event; already-negative withdrawals do not repeat overdraft; already-high balances do not repeat investment crossings. Every notification includes event name, customer name, CPF, branch, account number and *post-operation* balance. SMS and WhatsApp are distinct testable in-process recording implementations; recipient routing is determined by registered event subscriptions, not by the account naming sender classes.

## Constraints

Payment, transfer, and Pix remain inputs to the common withdrawal/deposit operations, never separate methods. SMS and WhatsApp stay local/in-process, testable without credentials/network. The account must not send messages or depend on concrete sender classes. Registration and callback must be dynamic and one-to-many, not a lone listener interface; publish only relevant events to currently registered interested observers; callback context must contain enough data to identify the changed account and format the required fields without requiring a snapshot of unrelated account internals. Separate the sender implementations outside the account; verify both independently and together. No dependency on external banking or messaging services. Do not change `.case/` during source work.
